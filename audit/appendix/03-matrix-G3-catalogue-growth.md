## Findings

1. **Product prices unvalidated end-to-end (negative/NaN accepted).** Device sends `retail_price`/`supply_price`/`markup` from free text (apps/provider/src/features/products/buildProductPayload.ts:22-25, :56-58; no client range check). Server POST only checks presence then `parseFloat` (apps/web/src/app/api/provider/products/route.ts:147, :194-195, :234-235); PATCH likewise (apps/web/src/app/api/provider/products/[id]/route.ts:93-94, :166-167). DB columns have no CHECK (supabase/migrations/074_product_catalogue_and_service_updates.sql:22-23; supabase/migrations/2851_product_variants.sql:34-35). Negative retail prices can be stored and flow into orders/inventory valuation.
2. **Service price validated only by DB CHECK, tier prices not at all.** POST `/api/provider/services` accepts any finite `price` (apps/web/src/app/api/provider/services/route.ts:270, :323); `pricing_options` (tier prices), `at_home_price_adjustment`, `tax_rate`, `service_cost_percentage` are stored raw (:333, :345-346, :349). PATCH uses `parseFiniteNumber` with no sign check (apps/web/src/app/api/provider/services/[id]/route.ts:81-88, :98, :136, :149) and stores `pricing_options` as-is (:143). Only `offerings.price >= 0` is enforced by DB (supabase/migrations/004_services.sql:96); negative tier prices in `pricing_options` JSON and negative `at_home_price_adjustment` are not blocked.
3. **Marketing campaign send/edit/delete/test-send bypass the `manage_marketing` permission.** Campaign list/create require `requirePermission("manage_marketing")` (apps/web/src/app/api/provider/campaigns/route.ts:124, :174) but PATCH/DELETE `/campaigns/[id]` (apps/web/src/app/api/provider/campaigns/[id]/route.ts:53, :150), POST `/campaigns/[id]/send` (apps/web/src/app/api/provider/campaigns/[id]/send/route.ts:22-25) and POST `/campaigns/test-send` (apps/web/src/app/api/provider/campaigns/test-send/route.ts:33-36) are `requireRoleInApi` role-only including `provider_staff`. Send and test-send debit marketing credits (test-send/route.ts:77-114; send → dispatchCampaign :45), so any staff member can spend the provider's paid credits.
4. **Packages POST/DELETE role-only with service-role client; PATCH requires permission.** POST `/api/provider/packages` uses `requireRoleInApi([owner,staff,superadmin])` and a service-role Supabase client (apps/web/src/app/api/provider/packages/route.ts:202, :205-214 — env var `SUPABASE_SERVICE_ROLE_KEY` by name); DELETE `/packages/[id]` same (apps/web/src/app/api/provider/packages/[id]/route.ts:266-267) while PATCH requires `edit_services` (:134). Inconsistent: staff without `edit_services` can create/delete packages but not edit them.
5. **Money-bearing settings writable by any staff (role-only auth).** `travel_fee` on zone selections POST/PATCH (apps/web/src/app/api/provider/zone-selections/route.ts:101; apps/web/src/app/api/provider/zone-selections/[id]/route.ts:68), `delivery_fee`/rates on shipping-config PUT (apps/web/src/app/api/provider/shipping-config/route.ts:80), booking-link slug PATCH (apps/web/src/app/api/provider/booking-link/route.ts:86), membership subscription cancel/reactivate/extend/win-back (apps/web/src/app/api/provider/membership-subscriptions/[id]/route.ts:31; …/extend/route.ts:29; …/win-back/route.ts:28) all use `requireRoleInApi` including `provider_staff` with no permission check, whereas sibling settings routes use `requirePermission('edit_settings')` (e.g. apps/web/src/app/api/provider/locations/route.ts:94, apps/web/src/app/api/provider/settings/online-booking/route.ts:131). Range validation on these fields is present (zod `min(0)`), but no upper bound.
6. **Promotion PATCH accepts out-of-range `value`.** POST validates percentage 0-100 / fixed > 0 (apps/web/src/app/api/provider/promotions/route.ts:97-103) but PATCH only rejects NaN (apps/web/src/app/api/provider/promotions/[id]/route.ts:172-181); DB CHECK is only `value > 0` (supabase/migrations/010_platform.sql:21), so a 500% discount can be set via PATCH when usage_count = 0. (Mobile screen does not send `value` on PATCH — promotions.tsx:152-184 — so exploitable only by direct API call.)
7. **Marketing credit top-up has a minimum but no maximum.** `amount_zar: z.coerce.number().min(10)` (apps/web/src/app/api/provider/marketing/credits/topup/route.ts:21); forwarded to Paystack (:86-102). Low risk (payer funds it) but an unbounded amount is unusual; role-only auth (:31) lets staff initiate.
8. **Add-ons and resource-groups are owner-only, stricter than the permission model.** POST/PUT/DELETE `/api/provider/addons*` require `["provider_owner"]` (apps/web/src/app/api/provider/addons/route.ts:117; apps/web/src/app/api/provider/addons/[id]/route.ts:88, :149); resource-groups POST/PATCH/DELETE require `[owner, superadmin]` (apps/web/src/app/api/provider/resource-groups/route.ts:80; …/[id]/route.ts:57, :143). Staff granted `edit_services`/`edit_settings` can manage services/resources but not add-ons/groups — functional inconsistency rather than a security gap; the mobile screens expose these actions to all users (settings/service-addons.tsx:107-109, resources.tsx:127-129).
9. **`/api/provider/reference-data` has no auth helper** — relies solely on RLS through `getSupabaseServer` (apps/web/src/app/api/provider/reference-data/route.ts:44-52). Data is non-sensitive lookup values; note for completeness.
10. **Test coverage is thin for money routes.** No `__tests__` for packages, promotions, membership-plans, addons, zone-selections, shipping-config, marketing credits/topup, campaigns send/test-send (see Routes table "Test file?" column). Only services and products collection routes have parity tests.
11. No screen in G3 calls a non-existent route; all 78 handler files exist. Legacy screens (catalogue-offerings-hub, catalogue-overview, advanced-pricing, packages-list, settings/shipping) are pure redirects/aliases.
