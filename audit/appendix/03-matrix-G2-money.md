## Findings

1. **POS `POST /api/provider/sales` trusts device-computed `subtotal`, `unit_price`, `discount_amount`, `tip_amount`.** Client sends all totals (apps/provider/app/(app)/(tabs)/sales.tsx:825-830, computed :531-543, items[].unit_price :823). Server uses `calculatedSubtotal = subtotal || Σ(unit_price×qty)` so any truthy client subtotal wins (apps/web/src/app/api/provider/sales/route.ts:615-616 and :683-684); line prices are not re-resolved from `offerings`/`products` (:740-741); `discount_amount` and `tip_amount` are written as sent (:618,:622,:686,:690,:708). Only tax is recomputed server-side (:620-621,:688-689); client `tax_amount`/`total_amount` are ignored (:555-561, :694). A `create_sales` user can therefore record arbitrary sale values. Contrast: `POST /api/provider/product-sales` (walk-in) re-prices from `products.retail_price` (provider/product-sales/route.ts:423-514) and the mobile walk-in screen sends no prices (walk-in-sale.tsx:622-636).
2. **Ads CPC budget amount is device-supplied and becomes the Paystack charge.** settings/ads.tsx:911,947 sends `budget` (parseFloat); provider/ads/campaigns/route.ts:311,:358 uses `Number(body.budget)` and inserts it as `ads_budget_orders.amount` (:416) with only a `budget <= 0` skip (:397) – no minimum/maximum or server-side price table (acceptable by design for CPC, but no floor). Pack models are safe (server price :332-351).
3. **Money-settings mutations guarded by role-only auth (incl. `provider_staff`), no permission check:** `PATCH /api/provider/settings/payments` (acceptCash/Card/Online, VAT, tips, `noShowFeeAmount`) – provider/settings/payments/route.ts:197 (roles :38-40), no inner check (:196-235); `POST /api/provider/ads/campaigns` + `POST …/[id]/checkout` (commits provider funds) – provider/ads/campaigns/route.ts:270, …/[id]/checkout/route.ts:46 (only `userHasProviderAccessAdmin`); `POST /api/provider/paycloud/terminals` (:121), `PUT/DELETE /api/provider/paycloud/terminals/[id]` (:21/:84), `PATCH /api/provider/paycloud/settings` (:59), `POST /api/provider/yoco/devices` (:184), `PUT/DELETE /api/provider/yoco/devices/[id]` (:143/:307). By contrast `GET /api/provider/paycloud/terminals` requires `process_payments` (:25) – stricter on read than on write.
4. **Auth inconsistency breaks staff reads: `GET /api/provider/settings/sales/taxes|tips|receipt` require `requireRoleInApi(["provider_owner","superadmin"])`** (taxes/route.ts:24, tips/route.ts:17, receipt/route.ts:15) while their PATCH uses `requirePermission(edit_settings)` (:72/:37/:75). Screens settings/tax-configuration.tsx:28, settings/sales-settings.tsx:24-26, settings/receipt-*.tsx and walk-in-sale.tsx:328 call these GETs; a `provider_staff` user with `edit_settings` gets 403 on load, and walk-in-sale falls back to `walkInTaxRate = 0` silently (walk-in-sale.tsx:382-385) – display-only, since product-sales recomputes VAT server-side.
5. **Paystack terminal `collection_intent` echoes client `expected_amount` without recomputation.** sales.tsx:902 sends `Number(grandTotal.toFixed(2))`; walk-in-sale.tsx:807 sends `Number(order.total_amount ?? cartTotalDue)`. Server returns it as `expectedAmount`/metadata (apps/web/src/lib/payments/paystack-terminal-provider-mobile-api.ts:482,:485) without deriving from the entity. Mitigated: later `allocate` caps to unallocated paid balance and order owed (lib :547-552, :640). Low risk; the displayed "expected amount" could mislead the customer.
6. **Sale subtotal path on POS: `subtotal ||` truthiness** means a legitimately 0 subtotal (100% discount) falls back to Σ items – fine – but a *non-zero wrong* subtotal is accepted (same root cause as #1). provider/sales/route.ts:615,:683.
7. **Units:** consistent. Rands (major) everywhere except Yoco which uses `amount_cents = Math.round(amount*100)` (src/components/payments/CardMachineCollectSheet.tsx:190; server accepts `amount_cents` or `amount`, yoco/payments/route.ts:31,:48-49,:92-93). PayCloud sends major units (PayCloudPaymentSheet.tsx:720-724) and server normalizes via `normalizePaycloudMajorAmount` (paycloud/payments/route.ts:107,:151). No cents/rands mismatch found. Note PayCloud sheet computes `totalAmount = amount + tip + cashback` only for display (PayCloudPaymentSheet.tsx:519); tip/cashback are sent as separate fields (:725-726) and server guards amount against expected (:181-207).
8. **Payout request** is correctly re-validated server-side (min, negative balance, available balance, RPC `insert_payout_request_guarded` with `p_max_available_before_reserve`) – payouts/route.ts:162-255, :367-373; client pre-checks are advisory (payouts.tsx:278-279 comment). No issue.
9. **Refund amounts** (product-orders.tsx:679-686) are clamped on device and re-clamped server-side from DB `total_amount − refunded_amount` (provider/product-orders/[id]/route.ts:178,:253-255). No issue.
10. **Payroll deductions** (pay-runs/[id].tsx:193-208) accepted as entered but server enforces min(0), draft-only, and recomputes `net_pay` (pay-runs/[id]/route.ts:15-19,:195,:237-249). No issue. `GET /api/provider/pay-runs/[id]` is role-only (:31) – staff may read a pay run containing other staff's pay (gating inside lib/payroll/payroll-access UNVERIFIED).
11. **Test coverage gaps on money mutations:** no `__tests__` next to `provider/sales/route.ts` (POST creates sales/ledger), `provider/paycloud/payments/route.ts`, `provider/paycloud/payments/[id]/{close,void,confirm}`, `provider/payments/route.ts` (Paystack terminal allocate), `provider/terminal-orders/[id]/initialize-payment`, `provider/invoices/[id]/initialize-payment` (test exists in parent dir only), `provider/pay-runs/[id]/{approve,mark-paid}`, `paystack/verify/route.ts` (writes 9 order tables with `optionalAuthInApi`), `provider/ads/campaigns/route.ts`, `provider/stripe-connect/onboard`.
