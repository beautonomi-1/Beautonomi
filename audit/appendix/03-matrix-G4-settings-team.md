## Findings

1. **Privilege escalation — any `manage_team` staff can create an owner-level staff account.** `POST /api/provider/staff` is gated only by `requirePermission('manage_team')` (`A/provider/staff/route.ts:365`), `role` is an unconstrained `z.string()` (`:332`), and `role === "provider_owner"` maps to `dbRole = "owner"` (`:445-448`) which is inserted as `provider_staff.role` (`:636`). `resolveStaffPermissionRow` returns **all permissions** for `role === "owner"` (`apps/web/src/lib/auth/permissions.ts:135-137`). The PATCH handler explicitly forbids this (`A/provider/staff/[id]/route.ts:393-402` "Only the business owner can assign the owner role") but POST has no equivalent guard, and no `requireStepUp` (contrast `reset-password/route.ts:18`, `invite/route.ts:37`, `permissions/route.ts:126`). A manager can therefore register a second email as a full owner (and `provider_manager`/`job:"manager"` grants `manage_finance`, `issue_refunds` — `apps/web/src/lib/provider/staff-invite-default-permissions.ts:55,:53` — which the creator may not hold; the per-staff permissions PATCH forbids granting unheld perms at `permissions/route.ts:225-233`, so POST bypasses that control).
2. **Privilege escalation — `is_admin` settable by `manage_team` staff.** `PATCH /api/provider/staff/[id]/settings` schema includes `is_admin: z.boolean().optional()` (`A/provider/staff/[id]/settings/route.ts:127`). Non-owner editors with `manage_team` are promoted to the full-schema path (`:215-222`), and `is_admin` is not stripped (only pay fields are filtered `:236-250`), so it is written to `provider_staff` (`:294-297`). `is_admin === true` yields **all permissions** (`lib/auth/permissions.ts:135`). Self-edit is limited to `STAFF_SELF_SETTINGS_KEYS` (`:158-168`), so this is a lateral→vertical escalation via another staff row (e.g., a second account). No step-up.
3. **Role editing bypasses the "cannot grant what you don't have" rule and step-up.** `POST /api/provider/roles` and `PATCH /api/provider/roles/[id]` accept arbitrary `permissions` records from anyone with `manage_team` (`A/provider/roles/route.ts:73-84,:104-107`; `A/provider/roles/[id]/route.ts:33-44,:87-90`) with no comparison against the editor's own permissions and no `requireStepUp`, unlike `staff/[id]/permissions/route.ts:126,:216-234`. Because a custom role takes precedence over direct permissions (`lib/auth/permissions.ts:151-163`), a `manage_team` staff whose own row has `role_id` set can PATCH their own role to all-true (self-escalation). Mitigating fact: no provider API path was found that sets `provider_staff.role_id` (only clears it: `permissions/route.ts:240-241`, `staff/[id]/route.ts:463`); see UNVERIFIED.
4. **`manage_team` staff can self-assign the `manager` preset via `PATCH /api/provider/staff/[id]`.** When `canManageTeam` is true the self-edit restriction is not applied (`A/provider/staff/[id]/route.ts:320-346` only restricts non-managers); `job:"manager"` → `updateData.role="manager"`, `permissions = preset.permissions` (`:459-462`) which includes `manage_finance`, `issue_refunds`, `process_payments` (`staff-invite-default-permissions.ts:50-55`). A staff member with custom perms `{manage_team:true}` only can thereby gain finance permissions. Contrast `permissions/route.ts:178-184` which blocks self-edits.
5. **Money-affecting commission settings are unvalidated.** `PATCH /api/provider/settings/team/commissions` has no zod; `service_commission_rate`/`product_commission_rate` = `Number(x)` with no 0–100 or NaN check (`A/provider/settings/team/commissions/route.ts:232-247`); tier `min_revenue`/`commission_rate` likewise (`:273-281`). Negative, >100 or `NaN` values reach `provider_staff` / `provider_staff_commission_tiers` (DB CHECK constraints UNVERIFIED). Same route also toggles `staff_share_cancellation_fee` (`:189-209`).
6. **Appointment timing/fee-adjacent settings unvalidated.** `PATCH /api/provider/settings/appointments` validates only the status enum (`A/provider/settings/appointments/route.ts:89-99`); `confirmationSlaHours`, `unconfirmedExpireHoursBeforeSlot`, `closeoutGraceMinutesSalon/AtHome`, `lateArrivalGraceMinutes` are written as received (`:112-126`) — no type, sign or range checks (affects auto-expiry/no-show/closeout behaviour).
7. **Cancellation policy fee bounds incomplete.** `fee_amount: z.number().min(0).optional()` with `fee_type: "percentage"` allowed and no `max(100)` or cross-field check (`A/provider/cancellation-policies/route.ts:15-16`; `[id]/route.ts:15-16`); `hours_before` has no upper bound (`:13`). `deriveEnforcementFields` does not clamp fee (`apps/web/src/lib/provider/cancellation-policy-enforcement.ts` — no fee handling found).
8. **Mutation routes with role-only auth (any `provider_staff`, regardless of permissions):** `POST /api/provider/automations` (`A/provider/automations/route.ts:100`), `PATCH/DELETE /api/provider/automations/[id]` (`…/[id]/route.ts:66,:162`) — enables/creates SMS/email automations (cost + customer-facing messaging); `PATCH /api/provider/customer-visibility` (`A/provider/customer-visibility/route.ts:64`); `POST /api/provider/twilio-integration/test` (`…/test/route.ts:17`) and `POST /api/provider/email-integration/test` (`…/test/route.ts:28`) — send paid test messages with the business's credentials. Other settings routes correctly use `requirePermission('edit_settings')`.
9. **Dead UI: time-off types CRUD can never succeed.** `settings/time-off-types.tsx` offers create/edit/delete (`S/settings/time-off-types.tsx:76,:168,:189,:204`) but the server returns `409 NOT_SUPPORTED` for POST (`A/provider/time-off-types/route.ts:97-101`) and PATCH/DELETE (`…/[id]/route.ts:50-52,:78-80`).
10. **Phone change does not reset `phone_verified`.** `PATCH /api/me/profile` writes `phone` as-is (`A/me/profile/route.ts:387`) and never touches `phone_verified` (`:449-454` only documents exclusion from client writes). Mobile verifies via Supabase OTP first (`S/settings-login-and-security.tsx:139,:164`), but the API itself accepts an unverified phone from any client while leaving the verified flag intact (DB trigger UNVERIFIED).
11. **Third-party credentials stored in plaintext columns (as far as the route shows).** Twilio `auth_token` and email `api_key`/`api_secret` are written directly to `provider_twilio_integrations` / `provider_email_integrations` (`A/provider/twilio-integration/route.ts:162-166`; `A/provider/email-integration/route.ts:163-167`) — no encryption call in the handler; masked on read (`:56`, `:55`). Column-level/pgsodium encryption UNVERIFIED.
12. **PII in server logs.** `POST /api/provider/staff` logs the invitee email (`A/provider/staff/route.ts:481`) and user ids (`:512,:594,:672`).
13. **Invite join URL (contains invite token) returned in error body.** On delivery failure `POST /api/provider/staff/[id]/invite` returns `join_url` to the caller (`A/provider/staff/[id]/invite/route.ts:165-175`). Caller is already `manage_team` + step-up, so low risk, but token exposure to client logs is worth noting.
